CUSTOMER DASHBOARD UI IMPROVEMENT ================================================== Improve the existing Customer Dashboard so it looks significantly more polished, modern, interactive, and professional. Do NOT completely replace the existing NearCart structure. Improve: - spacing - typography - card hierarchy - buttons - search area - filters - product cards - shop cards - reservation section - status indicators - empty states - hover states - loading states - responsive/mobile layout The dashboard should feel like ONE coherent NearCart product. Use clear visual hierarchy. Do not overuse: - gradients - glassmorphism - huge cards - excessive shadows - giant icons - random colors - unnecessary animations Use color only where it communicates useful information. ================================================== 2. USER-CONTROLLED SEARCH RADIUS ================================================== After the customer chooses/selects their nearby location, they must be able to choose HOW FAR NearCart should search. Current concept: LOCATION → SEARCH RADIUS → PRODUCTS/SHOPS The customer should NOT be forced to use a fixed definition of "nearby". Add a clear "Search Radius" control near the location/search controls. Example options: - 500 m - 1 km - 2 km - 5 km - 10 km - 25 km - 50 km The exact options can follow the existing application's distance implementation, but the user must be able to choose the radius. The meaning should be obvious: "Search within 2 km" "Search within 10 km" etc. The customer should be able to expand the search from: nearby shops → nearby bazaar → nearby area → nearby city without changing the fundamental search system. IMPORTANT: The selected radius must actually affect backend search results. Do NOT create a visual-only radius selector. The radius should be passed through the search request and used when calculating which shops/products are returned. The selected radius should remain visible while browsing results. Example: Location: Patna Junction Search radius: 5 km Results should only contain eligible shops within that radius. Changing to 25 km should refresh/recalculate the results. Use the existing distance calculation/service where possible. Do not create a second unrelated location system. ================================================== 3. IMPROVE SHOP CARDS ================================================== Existing shop cards/tablets need to become more informative and visually designed. Each shop result should clearly show the information that is ALREADY available in the database. Where available, show: - Shop name - Verification status - Rating - Number of reviews - Product availability - Product price - Distance from selected location - Estimated travel time if already supported - Open/closed status if existing data supports it - Reservation availability - Relevant product availability The card should make it easy for the customer to understand: "Can I get my product here?" "How far is this shop?" "Can I reserve it?" Use clear visual hierarchy. Example structure: SHOP NAME Verified ★★★★☆ 4.6 (128 reviews) ₹499 Available 750 m away ~5 min [Compare] [Reserve] Do not show fake values. If information does not exist in the database, do not invent it. ================================================== 4. COLOR HIGHLIGHTS FOR GOOD REVIEWS / TRUST ================================================== Improve visual communication for highly-rated shops and products. Use restrained semantic highlighting. For example: - High rating → subtle green highlight/badge - Verified shop → verification badge - Available → green status - Limited/uncertain availability → amber - Unavailable → red/neutral unavailable state Do NOT create fake "Best Shop", "Winner", "Top Seller" labels. Do NOT rank shops artificially. The rating and review count must come from actual database values. The purpose is simply to make useful information visually easier to understand. Example: ★★★★☆ 4.7 128 reviews can have a subtle positive visual treatment. ================================================== 5. REVIEWS MUST REQUIRE A REAL CUSTOMER-SHOP INTERACTION ================================================== A customer must NOT be able to post a review merely because they opened a shop page or product page. Review submission must require legitimate involvement with the shop. Preferred rule: A customer can review a shop/product only if the customer has completed a genuine transaction/reservation interaction with that shop. For the existing NearCart system: - A completed/collected reservation should qualify the customer to review. - Pending reservation should NOT qualify. - Rejected reservation should NOT qualify. - Cancelled reservation should NOT qualify. - Expired reservation should NOT qualify. - Simply viewing a product should NOT qualify. - Simply viewing a shop should NOT qualify. Connect the review eligibility check to existing reservation/order data. If the existing model uses Reservation as the transaction record, use it rather than creating an unnecessary duplicate system. Prevent duplicate reviews for the same eligible transaction/product where appropriate. The backend MUST enforce this rule. Do not rely only on hiding the review button in the frontend. The API/route must reject unauthorized review submissions. The customer UI should clearly explain why they can or cannot review. Example: "Review available after you collect your reservation." After successful collection: "Your purchase is complete. You can now review this shop/product." ================================================== 6. DIGITAL RECEIPT AFTER COMPLETED RESERVATION ================================================== Add a simple digital receipt to every successfully completed/collected reservation. Do NOT create an unnecessarily complicated accounting system. When a reservation reaches the final completed state, generate/store a digital receipt. The receipt should contain: - NearCart - Receipt number - Customer name - Shop name - Shop address - Product name - Quantity - Unit price - Total price - Reservation/order reference - Date/time - Payment method - Transaction status Example: -------------------------------- NEARCART DIGITAL RECEIPT Receipt: NC-000123 Shop: ABC Electronics Customer: Customer Name Product: Samsung 25W Charger Quantity: 2 Unit Price: ₹499 Total: ₹998 Payment: Pay at Shop Status: COMPLETED Date: 18 Sep 2026 -------------------------------- The customer should be able to: - View receipt - Access receipt from completed reservation - Download/print receipt if practical within the existing architecture Do not claim the receipt is a government/tax invoice unless the system actually supports that. If payment is only simulated, clearly label it appropriately. ================================================== 7. ONLINE PAYMENT OPTION ================================================== During reservation/checkout, provide a payment-method option: - Pay at Shop - Pay Online "Pay Online" does NOT need to be fully connected to a real payment gateway for this implementation. Example: Payment Method ○ Pay at Shop ○ Pay Online (Demo) If Pay Online is selected: - show a simple demo payment confirmation flow - update payment status appropriately - do NOT pretend that real money was transferred - receipt should show the selected payment method - clearly distinguish DEMO payment from real payment If a real payment integration already exists, preserve it rather than replacing it. Do not add a real payment provider unless already present. ================================================== 8. RESERVATION COUNTDOWN ================================================== Reservations must have a VERY visible countdown. The countdown becomes active/important once the shopkeeper approves/confirms the reservation. Example: RESERVATION CONFIRMED Your item has been reserved. Pickup must be completed within: 29:42 The countdown should continue in real time without requiring page refresh. When: 30:00 → 29:59 → 29:58 ... The UI should update automatically. Use the actual reservation expiry timestamp from the backend. Do NOT implement a fake frontend-only timer. The backend must remain the source of truth. If the existing reservation system currently uses a different expiry period, update it to the intended reservation-hold period used by NearCart. For the current NearCart design, use a 30-minute reservation hold after confirmation unless the existing business logic explicitly requires another configurable value. When the countdown reaches zero: - reservation becomes EXPIRED - reserved inventory must be released if inventory reservation exists - customer must clearly see that the reservation expired - Reserve/Pickup actions must no longer be available for that expired reservation ================================================== 9. When collected: "Reservation Completed" "Your digital receipt is ready." When rejected: "Reservation Rejected" Show the reason if the shopkeeper provides one. When expired: "Reservation Expired" "Your reservation hold has ended." ================================================== 10.
